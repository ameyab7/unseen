  Overview
  Unseen is a live, audio-only dating show: two verified strangers talk on air for about ten
  minutes, an AI host called Nova runs the show, and a city audience listens, votes and
  sends gestures. If both daters privately choose reveal, their photos unlock and a private
  chat opens.

  The MVP is done when a full show night runs end to end in one city: daters cast in
  advance, Nova hosting, a human moderator on shift, gestures paid through the app stores,
  and clips posted only with both daters' consent.

  Frontend
  Build the app in React Native with Expo and TypeScript, styled only from the design
  system's tokens, with TanStack Query for server data and LiveKit's React Native SDK for
  live audio.


  Framework and language
       Expo (React Native) with TypeScript in strict mode. Use development builds, not Expo
       Go, because LiveKit's WebRTC module and the ID-check SDK are native code.
       One language runs the app, the console, the Edge Functions and the shared schemas.
       A solo developer never switches context except for the AI host.
       EAS Build and Submit ship both stores from CI. EAS Update pushes JavaScript fixes
       over the air, so a broken screen can be fixed before tonight's show without waiting for
       review.


  UI and styling
       Plain StyleSheet plus a typed theme generated from the design system's tokens.json:
       two color themes, type scale, spacing, radii. Components never hard-code a hex value
       or font size; a lint rule enforces it.
       Bodoni Moda (bundled, open license) for display text at 24 px and up; the platform font
       everywhere else, so Dynamic Type and Android font scaling work.
       react-native-reanimated for the voice rings, sheets and the reveal; every animation
       checks Reduce Motion. React Native has no CSS clip-path, so the reveal's "lights up" is
       a scaled circular view over the daylight layer.
       Supporting libraries: @gorhom/bottom-sheet for sheets, phosphor-react-native for
       icons (as the design system specifies), react-native-svg for waveforms, expo-haptics
       for the reveal.


  State, routing and data
       Routing: Expo Router, file-based. Three tabs; the live room and the full-screen dater
       moments are modal stacks. Push notifications deep-link to a route, such as a cast seat
       or a show starting.
       Server state: TanStack Query over supabase-js, with database types generated from
       the schema. Anything transactional (a gesture, a seat request, a decision) calls a
       Postgres function, never several table writes from the client.

       Live state: the live room gets audio, captions and room events (poll open, gesture
       totals, the result) from LiveKit. Every event is validated against a shared zod schema.
       Local state: Zustand for session and player state (current show, mini-player, mute). A
       dater's night is an explicit state machine, cast → confirmed → backstage → on air →
       deciding → outcome, written as a typed reducer so illegal jumps cannot happen.
       Forms: react-hook-form with zod for the blind card and reports.
       Audio session: keep the show playing in the background (iOS background audio mode,
       an Android foreground service) and handle interruptions such as phone calls and
       Bluetooth switches. Lock-screen controls need a small native module; spike it in week

  Backend
  Run the backend on Supabase (Postgres, Auth, Storage, Realtime, Edge Functions) and
  LiveKit Cloud for audio, with Nova as one Python agent and managed vendors for ID
  checks, payments and push.




  system architecture · app, console, two platforms, Nova, five vendors

  The app talks to LiveKit for the show and to Supabase for everything else. Nova is the only
  server-side participant in a room, and every vendor reports back to Supabase through
  webhooks.


  Language and framework
       Supabase is the backend. Postgres row-level security (RLS) is the authorization layer,
       its REST layer serves plain reads, Postgres functions handle every transactional write,
       and Edge Functions (TypeScript) handle webhooks and anything holding a secret.
       Nova is a Python worker built on LiveKit Agents and hosted on LiveKit Cloud. Python
       because the framework's speech plugins and turn handling are most complete there; a
       Node.js version exists if you want TypeScript only.

  The privacy promise "nobody learns who chose what" is enforced in the database, not the
  UI:

     create table date_decisions (
         date_id uuid references dates(id) on delete cascade,
         user_id uuid references profiles(id),
         choice text not null check (choice in ('reveal', 'unseen')),
         decided_at timestamptz not null default now(),

         primary key (date_id, user_id)
     );
     alter table date_decisions enable row level security;


     create policy "read only your own decision" on date_decisions
         for select using (user_id = auth.uid());


     create policy "decide once, while deciding" on date_decisions
       for insert with check (
             user_id = auth.uid()
             and exists (select 1 from dates d
                                      where d.id = date_id and d.status = 'deciding'
                                        and auth.uid() in (d.dater_a, d.dater_b)));


     -- Called by the show runner when both have decided or the window closes.
     create function resolve_date(p_date uuid) returns text
     language plpgsql security definer set search_path = public as $$
     declare v_reveals int;
     begin
         select count(*) into v_reveals from date_decisions
          where date_id = p_date and choice = 'reveal';
         update dates
            set outcome = case when v_reveals = 2 then 'mutual' else 'not_mutual'
     end,
                       status = 'ended'
          where id = p_date;
         if v_reveals = 2 then
             insert into matches (date_id, user_a, user_b)
             select id, dater_a, dater_b from dates where id = p_date;
         end if;
         return (select outcome from dates where id = p_date);
     end $$;
     revoke execute on function resolve_date(uuid) from public, anon,
     authenticated;

  Live-room events are not HTTP. Nova's show runner publishes them into the LiveKit room:
  show state, date state, poll open, poll result, gesture totals, lightning round unlocked,
  result announced. Captions arrive as LiveKit transcription streams. Every event's shape
  lives in packages/shared .


  Authentication and authorization
       Supabase Auth with Sign in with Apple, Google and phone codes over SMS. Offering
       Apple sign-in next to Google keeps the App Store's login rule satisfied.
       Roles ride in the access token through a custom token hook: listener, phone-verified,
       dater (ID verified), moderator, admin.
       RLS is the authorization layer. Every table has policies, and a pgTAP test proves who
       can and cannot read it. The decision and reveal-photo policies matter most.
       LiveKit tokens are minted on the server with the smallest grants: listeners only
       subscribe, a dater can publish audio only during their own slot, and the moderator joins
       hidden.
       Age: a self-declared birthday at sign-up, then the ID check before going on air. An ID
       showing under 18 closes the account.


  Real-time audio and the AI host
       LiveKit Cloud runs one room per show. Daters and Nova publish; listeners subscribe.
       Egress records each date to private storage for clips and safety review; a retention job
       deletes it afterward.
       Nova is a show runner first and a chatbot second. A deterministic state machine walks
       the running order; the language model only writes the lines inside each beat.

       Speech pipeline: streaming speech-to-text, then a small fast language model, then a
       branded text-to-speech voice. A speech-to-speech model is quicker to build but leaves
       no text checkpoint, and Nova's own lines must pass the same guardrails before they
       are spoken. Settle it with a bake-off in weeks 1 and 2.
       The same transcripts feed captions and moderation. A fast classifier plus a personal-
       details detector flags harassment, sexual content, hate, minors, and addresses or
       workplaces. Nova can redirect or mute instantly; ending a date or banning someone
       needs the human moderator to confirm in the console.

  Development workflow with Claude Code and VS Code
  Use Claude Code as a fast pair programmer inside VS Code: conventions written once in
  CLAUDE.md, one feature slice per session, and every change still reviewed and tested by
  a person.


  Setup
   1. Install the Claude Code extension from VS Code's Extensions view (search "Claude
      Code"); it needs VS Code 1.98.0 or newer. To also run claude in the integrated terminal,
       install the standalone CLI (VS Code guide).
   2. Open the repository root and run /init to generate a first CLAUDE.md, then cut it
      down to the conventions below. Keep it under 200 lines; longer files lower adherence
      (memory guide).
   3. Add a nested CLAUDE.md in apps/mobile , supabase and services/nova . Nested
       files load only when Claude works in that folder, so each session carries only what it
       needs (monorepo guide).
   4. Put narrow rules in .claude/rules/ with paths frontmatter, for example a migrations
       rule that loads only for supabase/migrations/** .
   5. Commit a project .claude/settings.json : allow typecheck, lint, tests and the local
       Supabase stack; deny reading .env files and any command that reaches staging or
       production (permissions).
   6. Add hooks that run the formatter and linter after every edit, and typecheck plus tests
      before a commit. CLAUDE.md is guidance Claude can miss; hooks always run (hooks
      guide).
   7. Connect MCP servers for GitHub and Sentry, and Supabase pointed at your local
      project only (MCP).

  Breaking features into tasks
  A good task is a vertical slice Claude can finish, test and hand back in one session: one
  pull request, a few hundred changed lines, one demoable result. Inside a slice, work
  bottom-up so each layer is tested before the next one depends on it:

   1. Migration, RLS policies and pgTAP tests.
   2. Postgres function or Edge Function, with tests for its failure cases.
   3. Shared zod schema for any payload or room event.
   4. Data hook in src/features .
   5. UI components in src/ui , each added to a dev-only gallery screen showing every
       state.
   6. Screen wiring, then one Maestro end-to-end flow for the happy path.

  For example, "decision and reveal" becomes six tasks: the decisions migration and its
  tests; the decide function; the result event in packages/shared and Nova emitting it; the
  decision screen with its countdown and timeout; the reveal and not-a-match screens with
  their reduced-motion versions; and one Maestro flow from decision to first chat message.
  Run parallel tasks, such as console work beside app work, in separate git worktrees so
  their changes never collide (worktrees).
